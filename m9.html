9.1. Сім ролей системи ↑ зміст

Роль визначає які розділи кабінету доступні користувачу і що він бачить на головній сторінці після входу. Два способи отримати роль: обрати самостійно при реєстрації або отримати від адміністратора.

librarian_pro

Бібліотекар-фахівець лише адмін

Штатний бібліотекар, методист

  • Регіональний зріз (діячі і установи регіону)
  • PDF-конструктор з пресетами
  • Популярні книги і новинки
  • Вибране, підписки, Читальня
librarian_community

Бібліотекар-спільнота

Обирається при реєстрації

  • Вибране, підписки
  • Регіональний зріз якщо вказано регіон
  • PDF-конструктор
  • Читальня
researcher

Дослідник

Обирається при реєстрації

  • Бібліографічні корпуси / папки
  • Вибране з прив'язкою до папок
  • Автоматично: перша папка «Моє перше дослідження»
  • Публічний шеринг папок
author

Автор

Обирається при реєстрації

  • Форма верифікації → прив'язка до картки Person
  • Після верифікації: метрики залученості
  • Збереження книг, цитування, завантаження PDF
educator

Освітянин лише адмін

Педагог, викладач

  • Профілі учнів і читацькі щоденники
  • Бібліографічні корпуси / папки
  • PDF-конструктор
  • Популярні книги і новинки
parent

Батьки

Обирається при реєстрації

  • Профілі дітей (ім'я або псевдонім + рік народження)
  • Читацькі щоденники для кожної дитини
  • Зведення: читає / прочитала / хоче прочитати
other

Інше

Обирається при реєстрації

  • Вибране, підписки
  • Пошук і Машина Часу
  • Мінімальний кабінет

Friction-triggered реєстрація

Портал не просить реєструватись одразу. Модальне вікно реєстрації з'являється лише коли незареєстрований користувач натискає «Зберегти», «Підписатись» або іншу дію що потребує кабінету. Дія зберігається в сесії і виконується автоматично після входу — користувач бачить одразу результат, а не порожній кабінет.

9.3. Профілі користувачів ↑ зміст

Шлях: Accounts → User Profiles. Фільтри: за роллю, за статусом розсилки. Пошук: ім'я, email, текст «Про себе».

Ключові поля профілю

ПолеОписХто заповнює
roleРоль — визначає функціонал кабінетуКористувач при реєстрації або адмін
regionРегіон з REGION_CHOICES. Якщо порожній — береться з установиКористувач в налаштуваннях
institutionFK → InstitutionPage. Використовується для регіонального зрізуКористувач в налаштуваннях
verified_personFK → Person. Прив'язує обліковий запис до картки діяча. Тільки для role=authorАдмін після розгляду запиту
receive_newsletterДозвіл на email-розсилки. Без ✅ підписки не надсилають листиКористувач в налаштуваннях
avatarЗображення профілюКористувач

Підводний камінь з підписками

Користувач може мати активні підписки але не отримувати листів якщо: не вказаний email, або receive_newsletter = False. Це не помилка системи — перевіряти при зверненнях про «не приходять листи».

9.4. Верифікаційні запити авторів ↑ зміст

Автор з роллю author може надіслати заявку на прив'язку до картки діяча в каталозі. Після верифікації він отримує доступ до метрик залученості.

Шлях: Accounts → Verification Requests. Фільтр за статусом pending — показує незрозглянуті.

Порядок розгляду заявки

1

Відкрити запит зі статусом «pending»

Побачите: ім'я користувача, яку картку Person обрав, коментар або посилання для підтвердження (наприклад, Facebook-сторінка або сайт автора).

2

Верифікувати відповідність

Порівняти ПІБ облікового запису з ім'ям у картці Person. Перевірити посилання або коментар. Якщо є сумніви — написати користувачу через email з профілю.

Перевіряти також чи не прив'язана ця картка Person до іншого облікового запису.

3

Якщо підтверджено → заповнити verified_person

Відкрити UserProfile цього користувача (Accounts → User Profiles → пошук за email) → поле verified_person → autocomplete → обрати відповідного діяча → зберегти.

4

Оновити статус запиту

Повернутись до запиту → поле «Status» → approved або rejected → зберегти. Користувач побачить зміну в кабінеті.

СтатусЗначенняЩо далі
pendingОчікує розглядуПереглянути регулярно — не залишати довго
approvedПідтвердженоverified_person встановлено, автор бачить метрики
rejectedВідхиленоАвтор може подати нову заявку з іншим діячем

Що отримує автор після верифікації

  • Кількість книг у базі КЛЮЧА
  • Скільки разів його книги додали у Вибране
  • Скільки разів зберегли його профіль діяча
  • Цитування публікацій через CitationEvent
  • Завантаження PDF-матеріалів профілю та книг

9.5. Призначення привілейованих ролей ↑ зміст

Дві ролі користувач не може обрати самостійно при реєстрації — їх призначає адміністратор:

РольДля когоЩо додається порівняно з базовою
librarian_proШтатний бібліотекар, методист НБУ для дітей і мережіПовний регіональний зріз, PDF-пресети, пріоритет у аналітиці
educatorПедагог, викладач що веде роботу з учнямиПрофілі учнів і щоденники + корпуси + PDF-конструктор

Порядок призначення

1

Accounts → User Profiles → знайти профіль

Пошук за email або ім'ям. Переконатись що це правильний користувач.

2

Поле «Role» → обрати librarian_pro або educator → зберегти

Зміна набуває чинності одразу — при наступному вході користувач побачить розширений кабінет.

Якщо користувач вже в системі — кабінет оновиться без виходу і повторного входу.

Як користувач запитує привілейовану роль

Стандартного механізму запиту немає — користувач звертається через email або особисто. Фіксуйте підставу призначення в полі «Про себе» або в «Службових коментарях» якщо потрібна внутрішня нотатка.

9.6. Вибране, підписки, щоденники ↑ зміст

Вибране (Favorites)

Accounts → Favorites. Кожен запис: користувач + тип контенту + ID об'єкта + нотатки + папка. Дублів не буває (unique_together). Видаляти тільки якщо запис помилковий або за скаргою користувача.

Підписки (Subscriptions)

Accounts → Subscriptions. Масові операції: позначити чекбоксами → Активувати / Деактивувати / Видалити. Частота: instant / daily / weekly.

Умова отримання листів — три компоненти

  • У профілі вказано email
  • receive_newsletter = True у UserProfile
  • Підписка має is_active = True

Читацькі щоденники (Reading Logs)

Accounts → Reading Logs. Кожен запис прив'язаний до профілю дитини (ChildProfile). Поле book_title_raw — вільний текст якщо книги немає в базі КЛЮЧА; поле book — FK до BookPage якщо є. Не редагувати записи без звернення від користувача.

PDF-пресети (PDF Builder Presets)

Accounts → PDF Builder Presets. Збережені налаштування Конструктора PDF. Видаляти тільки якщо є скарга або пресет помилковий. З поля filter_state_json доступні: object_type (book/person), anniversary_year.

9.7. Моніторинг і регулярні перевірки ↑ зміст

Щотижня

Верифікаційні запити

  • Accounts → Verification Requests → фільтр pending
  • Розглянути всі нові заявки
  • Не залишати pending більше тижня
Щомісяця

Профілі без email

  • Не отримають жодного сповіщення
  • Підписки для них неефективні
  • Перевірити через shell-запит нижче
Щомісяця

Активні підписки з newsletter=False

  • Підписки є, але листи не надсилаються
  • Технічно коректно, але варто відстежувати
За потреби

Топ тегів і матеріалів

  • Які теги найпопулярніші для підписок
  • Які матеріали найчастіше зберігають
  • Для редакційних рішень і пріоритетів

Корисні запити через Django shell

Запуск: docker-compose exec web python manage.py shell

# Кількість профілів за роллю
from accounts.models import UserProfile
from django.db.models import Count
UserProfile.objects.values('role').annotate(
    count=Count('id')
).order_by('-count')

# Верифікаційні запити що очікують
from accounts.models import VerificationRequest
VerificationRequest.objects.filter(status='pending').count()

# Активні підписки з newsletter=False (лист не надійде)
from accounts.models import Subscription
Subscription.objects.filter(
    is_active=True,
    user__userprofile__receive_newsletter=False
).count()

# Топ-10 тегів для підписок
Subscription.objects.values('tag__name').annotate(
    count=Count('id')
).order_by('-count')[:10]

# Найбільш збережені матеріали (топ-20)
from accounts.models import Favorite
Favorite.objects.values(
    'content_type__model', 'object_id'
).annotate(count=Count('id')).order_by('-count')[:20]

Масове видалення — погодити з командою

Операції на кшталт Subscription.objects.filter(is_active=False).delete() виконувати лише після погодження. Неактивні підписки — не сміття: користувач міг призупинити навмисно.

Чеклист M9 ↑ зміст

Щотижня

Accounts → Verification Requests → фільтр pending → розглянути всі нові заявки
Після затвердження: verified_person встановлено в UserProfile → статус запиту → approved

При призначенні привілейованої ролі

Accounts → User Profiles → знайти профіль за email
Поле Role → librarian_pro або educator → зберегти
Підставу призначення зафіксовано (в листуванні або в нотатках профілю)

При скарзі «не приходять листи»

Перевірити що email вказано в профілі
Перевірити receive_newsletter = True в UserProfile
Перевірити що підписка has is_active = True

Щомісяця

Запустити shell-запит: кількість профілів за роллю — для звітності
Перевірити топ тегів підписок — для редакційних пріоритетів
Перевірити топ збережених матеріалів — для розуміння попиту
